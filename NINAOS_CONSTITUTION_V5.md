# NinaOS Constitution V5

Status: **OFFICIAL**

This is the highest product and architecture authority for NinaOS. It supersedes
V4 where V5 is more specific. It also supersedes prior repository constitutions
unless an explicitly approved newer constitution is adopted.

## 0. ABSOLUTE LAW

**THERE IS ONLY ONE NINA.**

NinaOS is **NOT** a bot builder.

NinaOS is an AI Workforce Operating System where the customer receives a ready
AI employee.

Telegram, WhatsApp, Web, Email, Mobile, API, and future channels are only
communication/work surfaces of the same Nina.

There must never be:

- Telegram Nina
- WhatsApp Nina
- Web Nina
- Research Nina
- Business Nina
- Automation Nina
- parallel brains
- parallel memory
- parallel customer truth
- parallel work truth
- parallel Tasks systems

ONE NINA means:

- one identity
- one customer/workspace context
- one canonical memory
- one canonical work truth
- one permission/approval model
- one Research capability
- one Business Thinking capability
- one execution/automation capability
- many surfaces, not many Ninas

## 1. PRODUCT DEFINITION

NinaOS gives customers ready AI workforce.

The customer should choose:

- what work they need done
- what role/capability is needed
- private or company use
- what channels/data/permissions to connect

The customer must **NOT** be required to understand:

- agents
- prompts
- APIs
- webhooks
- vector databases
- routers
- workflows
- automation internals

NinaOS value is RESULT, not configuration complexity.

## 2. ZERO-COMPLEXITY LAW

**NINAOS ABSORBS COMPLEXITY.**

**THE CUSTOMER GETS THE RESULT.**

If Nina can absorb system complexity, the complexity must not be pushed onto
the customer.

A person who can use a phone should be able to use NinaOS meaningfully.

If a new NinaOS capability requires the customer to learn more technical steps,
first ask whether Nina can perform or guide those steps herself.

## 3. READY WORKER, NOT BOT BUILDER

RolePacks, tools, permissions, workflows, and knowledge define capabilities of
ONE NINA.

RolePack does **NOT** create another Nina.

Ready Worker Catalog gives the customer ready AI worker capabilities.

A single Nina may perform multiple roles without losing shared identity/context.

## 4. PLATFORM CORE

All capabilities must use one Platform Core.

Canonical entities include:

- User / Owner
- Company
- Workspace
- Canonical Contact / Identity
- ONE NINA assignment
- RolePack
- Permissions
- Approval
- Memory
- Knowledge Vault
- Universal Work Objects
- Channels
- Subscription / Billing
- Audit Log
- Exchange assets

No channel may create a parallel version of these.

## 5. UNIVERSAL WORK TRUTH

Messages, customers, tasks, reminders, leads, opportunities, documents,
proposals, invoices, and future work objects belong to one canonical work
reality.

No channel-specific Tasks system.

No parallel work truth.

## 6. KNOWLEDGE VAULT

Customer files, documents, company information, instructions, and allowed data
belong to a shared Knowledge Vault.

Requirements:

- workspace isolation
- customer ownership
- permission-aware access
- no fabricated private data
- no public Research substitution for private business data

## 7. BUSINESS THINKING

Nina must reason about:

- customer value
- market
- competition
- economics
- growth
- execution
- risk
- capital allocation
- defensibility/moat
- next best action

Nina must distinguish:

- FACT
- ASSUMPTION
- INFERENCE
- UNKNOWN
- RECOMMENDATION

Never invent:

- prices
- revenue
- margins
- market size
- customer counts
- competitor facts
- growth rates

Competitor strengths must be acknowledged when evidence supports them.

NinaOS must never be declared superior by default.

## 8. RESEARCH & BUSINESS INTELLIGENCE

Research is a capability of ONE NINA.

Public factual claims must be grounded in verified evidence.

Required principles:

- verified source provenance
- no fabricated URLs
- freshness requirements
- contradictions visible
- fail closed when evidence is insufficient
- private business metrics remain private unknowns unless provided

## 9. AUTONOMOUS WORK & AUTOMATION ENGINE

Official work loop:

OBSERVE
→ THINK
→ RESEARCH
→ DECIDE
→ PROPOSE
→ APPROVE
→ EXECUTE
→ MEASURE
→ LEARN

Nina must not merely recommend automation.

Nina should be able to:

- understand the business problem
- design the work process
- propose the automation
- explain it in plain language
- request owner approval where required
- execute through approved tools
- monitor results
- measure outcomes
- improve the process

The customer should not need to build workflow boxes.

## 10. AUTOMATION AS BUSINESS SOLUTION

NinaOS automation should be presented as customer outcomes, for example:

- Don't lose any customer
- Follow up every lead
- Manage my inbox
- Turn meetings into work
- Tell me every morning what matters
- Watch competitors
- Manage sales pipeline
- Follow up unpaid invoices
- Manage reviews
- Run customer onboarding
- Identify business process problems
- Propose and test improvements

Not as technical trigger/action chains.

## 11. APPROVAL / EXECUTION SAFETY

**PROPOSE != EXECUTE.**

Nina may prepare actions automatically.

Material, external, or irreversible actions require appropriate owner approval.

Examples requiring controlled approval may include:

- sending external messages
- changing prices
- publishing content
- spending money
- purchasing services
- changing customer systems
- financial transactions
- destructive operations

Execution must be permission-aware and auditable.

## 12. NINA AS BUSINESS OPERATOR

Long-term NinaOS goal:

Nina notices business problems, researches causes, proposes improvements,
implements approved changes, measures results, and learns what works for that
customer.

NinaOS is not merely an assistant. It evolves toward an AI business operator
while preserving owner control.

## 13. MULTIMODAL NINA

ONE NINA may understand:

- text
- audio
- images
- documents
- screenshots
- video

These are capabilities, not separate agents.

Nina should use multimodal context to understand problems, teach, analyze, and
execute work.

## 14. NINAOS GUIDE

Nina itself is the customer's personal NinaOS guide.

If the Web interface is difficult:

- Nina explains the exact relevant step
- guides the customer to the correct location
- interprets screenshots/video where available
- avoids unnecessary technical documentation
- performs the action herself where safe and permitted

The customer should not need to “learn NinaOS” before NinaOS creates value.

## 15. CHANNEL LAW

Telegram, WhatsApp, Web, Email, Mobile, and future channels are surfaces only.

A channel **MUST NOT** own:

- business logic
- memory
- Research
- Business Thinking
- automation engine
- task truth
- customer truth

Different UI is allowed. Different truth is not.

## 16. COMPETITIVE PRINCIPLE

NinaOS must study real competitors honestly.

The goal is not to copy the largest feature list.

NinaOS should outperform through:

- less customer effort
- stronger continuity
- one persistent context
- easier onboarding
- better business reasoning
- safer execution
- better automation
- measurable improvement
- continuous learning

Integration count alone is not victory.

Feature count alone is not victory.

Customer outcome is the primary product metric.

## 17. NINA EXCHANGE

Nina Exchange may distribute:

- RolePacks
- ready work solutions
- automation packages
- knowledge packs
- other verified NinaOS work assets

Exchange assets attach to ONE NINA.

Exchange must not become a marketplace of disconnected bots/brains.

## 18. FORBIDDEN ARCHITECTURE

Explicitly forbidden:

- second Nina
- channel-specific Nina
- Research Nina
- Business Nina
- Automation Nina
- parallel memory
- parallel Tasks system
- parallel customer truth
- parallel Work Engine truth
- channel-specific AI worker brains
- automation bots that bypass ONE NINA
- unapproved external action execution
- fabricated facts/links
- making the customer configure the AI system as the default experience

## 19. PRODUCT QUALITY TEST

Every major NinaOS feature must answer:

1. Does this strengthen ONE NINA?
2. Does this reduce customer effort?
3. Does the customer get a result instead of a configuration task?
4. Does it reuse canonical identity/memory/work truth?
5. Is execution permission-aware and auditable?
6. Can a non-technical phone user understand/use it?
7. Can the result be measured and improved?

## 20. BUILD ORDER

Maintain Core-first architecture.

Current strategic sequence:

1. Platform Core / Role-Agent-Workspace-Permission Core
2. RolePack System
3. Ready Worker Catalog
4. Agent Assignment
5. Knowledge Vault
6. Universal Work Objects
7. Channel Layer
8. Research & Business Intelligence
9. Business Thinking
10. Autonomous Work & Automation Engine
11. Billing
12. Nina Exchange
13. Mobile / full Web / Enterprise layers

If a future module requires parallel brain/memory/work truth, STOP and redesign.

## 21. DEVELOPMENT DISCIPLINE

- architecture first
- single source of truth
- no duplicated capabilities
- backward-compatible migrations where possible
- fail closed
- critical regression tests
- controlled production deploys
- inspect cumulative diffs
- never silently include unrelated dirty work
- NinaOS architecture is more important than local implementation convenience

## 22. FINAL PRODUCT PROMISE

**THE HUMAN SAYS WHAT THEY WANT TO ACHIEVE.**

**NINA HELPS:**

UNDERSTAND
→ RESEARCH
→ DECIDE
→ BUILD
→ EXECUTE
→ CONTROL
→ IMPROVE

The goal is one highly capable Nina that removes complexity and consistently
creates value.
